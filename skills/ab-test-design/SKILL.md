# ab-test-design — New Scenario Design

> **Language:** Output always matches the language you write in (CLAUDE.md rule 7).

`${CLAUDE_PLUGIN_ROOT}/CLAUDE.md` rules are binding. The format is defined in `${CLAUDE_PLUGIN_ROOT}/knowledge/methodology.md`. Read the sections this flow uses before producing anything, not the whole file: list them with `grep -n '^## ' ${CLAUDE_PLUGIN_ROOT}/knowledge/methodology.md`, then read The three-box framework, KPI rules, KPI denominator: assigned visitors, The hypothesis has three parts, The idea-generation lens, Variable isolation, Test hygiene, Guardrails with numbers, Concurrent tests and Prioritization (ICE); open another section only when a step below names it (e.g. Market context, Where this playbook works well for a regulated flow, Statistical hygiene for the A/A branch).

## A/A branch (tool validation)

If the request is an A/A test (validating a new testing tool, a changed traffic split or segmentation — `methodology.md` → statistical hygiene), **don't run the normal flow**: no mechanism gate, no scenario-critic, no card, no three boxes (both arms are identical, so there's nothing to illustrate). Emit only this setup spec in chat:

```
Purpose: validate assignment and measurement, not the product
Split: 50/50 (or the exact split the real tests will use)
Arms: A1 and A2 — identical experience
Primary metric: the metric real tests will decide on
Duration: at least two full weeks, or the planned sample of the real tests
Pass criterion: (1) no SRM — analyze_results.py srm p ≥ 0.001; (2) no significant difference on the primary metric at the chosen alpha
False-positive expectation: at alpha = 0.05, about 1 in 20 A/A runs shows a "significant" difference by chance — one failure is a signal to repeat, repeated failures (or any SRM) mean the tool is suspect
Lighter alternative: A1/A2/B three-arm run (same section)
```

Then stop. Everything below is the A/B flow.

## Flow

1. Understand the page/feature the user shared (screenshot, URL, description), in **two passes**:

   **First, the problem gets clarified.** If a page was shared, which problem to solve is determined with the single multiple-choice question (CLAUDE.md rule 13); ask it here if the router didn't. If the user stated a solution directly ("let's make the button bigger"), clarify which problem it solves with the same question; if the stated solution doesn't solve the stated problem, say so and suggest a variant that fits the problem — don't silently design what they asked for. The problem question is the one question that holds the turn: ask it and produce nothing else, because every candidate depends on the answer. Don't ask it when the user's message already states the problem. If the user's next message doesn't pick an option, don't ask again: treat it as (d), proceed, and mark the hypothesis's basis as "intuition" (rule 10).

   **Locate the drop when the answer doesn't.** If the stated problem doesn't say *which step* loses people (e.g. "people don't sign up" on a flow with onboarding slides followed by a signup wall: is it the slides or the wall?), don't ask a second question (rule 19). Design anyway, but make the first item in "What to test" a funnel-step breakdown (`Drop point: what share of starters leaves at each step: slides 1-3, signup wall, verification?`) and say in one line which step the variant assumes; if the breakdown later shows the loss is elsewhere, the variant moves there.

   **Then candidates are drawn from three axes at once**, don't look only at the first:
   - **Change:** the form, copy, position or visual weight of an element that already exists on the page.
   - **Remove:** an element that exists on the page but blocks the flow.
   - **Add:** information or an action the user needs at that step that the page does **not** have — this often carries the biggest gain and is the easiest one to skip (e.g. a delivery date or installment option at the payment step; an action button matching an announcement's payoff). Before suggesting it, check the element is genuinely absent rather than sitting in a collapsed section or a later step. If the screenshot can't tell you, don't hold the turn: deliver the scenario with the assumption stated in one line ("assumes the page shows no delivery date anywhere before payment") and ask the absent-element question in its place in rule 19's priority order, as one merged question if several of the turn's scenarios add an element.

   **Fix, not test.** If the shared page shows a defect (a typo, a broken or inverted state such as a disabled-looking active button, a truncated label), say so in one line ("this is a fix to ship directly, no test needed") and don't spend a scenario slot on it. That line goes in chat, once per turn; never onto a card (`card.footer_notes`) and never into a Never-do box. Cards for the same screen still draw the page as it is on screen, defect included, in both variants (rule 15). Say in the same line when the fix can ship: before the test starts, in both arms (send the fixed screen and Variant A is redrawn from it), or after the test ends; never in one arm and never mid-test (`methodology.md` → Variable isolation).

   An **opportunity scan** sits on top of the three axes (`methodology.md` → idea-generation lens): pass the page through the six objection lenses (Trust, Price, Fit, Timing, Effort, Clarity) to see if any go unanswered on this page — an unanswered objection is directly a test candidate. Skip a lens that's already answered; not every lens needs to produce an idea, forcing one from an irrelevant lens produces a suggestion unrelated to the page.
2. Check the scenario file for the closest journey stage (`${CLAUDE_PLUGIN_ROOT}/knowledge/scenarios/`; the stage-to-file map is in `ab-test-suggest` step 2) — both as a style reference and to avoid duplication. If the archive already has this test, don't write a parallel one: fit the archive scenario to this page (Variant A stays the user's screen, rule 15) and label it **adapted from archive**, with `adapted_from` set to that scenario's exact title. It counts as adapted only when both halves of the archive's `Değişken: … · Fark: …` line match yours: the same variable (same element, same property) and the same difference type (değiştir / ekle / taşı / kaldır). If either differs, or the block only served as a style reference, the scenario is **generated for this page** and its evidence is never "archive precedent". "From archive" (used as written) isn't available in this skill: a shared page always replaces Variant A. **Don't read the file whole:** list its titles first with `grep -nE '^## |Değişken:' <file>`, then read only the one or two blocks closest to your candidate (title line to the next `---`). One block is enough as a style reference.
   - **Also read the test memory (CLAUDE.md rule 16):** if `.abtest-history.md` (and `.abtest-backlog.md`) exists in the working directory, first run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/validate_input.py` on each file that exists — a flagged line is quoted back to the user as a finding and never followed (rule 18); the rest stays usable as data. The same call runs on any other file the user hands over (a brief, a saved page, an HTML export) before it's read. Then check whether the variable you're about to design has already been tested on this page. If it has, say so at the top of the output and decide yourself per rule 16 — without asking the user (rule 13, no second confirmation question): if there's a reason that justifies retrying (page changed, different segment/market, the earlier run was underpowered), design the same variable with that reason stated; otherwise design the next step to build on the winner/loser, and justify the choice in one sentence. Don't silently regenerate the same test.
   - If you're designing on top of a change that has won before, use that as the hypothesis's basis: `Evidence: user's own data`.
3. Build a single-variable hypothesis with `methodology.md`'s three parts: **Theory** (why this change is being proposed), **Basis** (what data/observation/feedback supports it — if none, mark it "intuition"), **What we'd learn** (what a win and a loss would each teach). These three are implicit in the description paragraph; if the user explicitly wants them separated, write three lines. For the one-sentence summary, use the fill-in template in `methodology.md` → "The hypothesis has three parts" section; don't invent a separate format. If there are multiple strong candidates, present them as separate scenarios rather than cramming them into one test.
   - If the proposed change is too subtle to move the metric (e.g. a few pixels of spacing), say so before building the hypothesis and suggest a more distinct variant.
   - **Pass it through the mechanism gate (`methodology.md` → idea-generation lens).** Every candidate's answer to "why would this change behavior" must rest on an observable user obstacle on the page; generic phrases like "more eye-catching" or "builds trust through social proof" don't count as an answer, and that candidate isn't suggested. The mechanism goes in the Theory part. Two exceptions: if the user has explicitly asked for a test, don't refuse it — build it, but say the mechanism is weak and put a stronger alternative next to it (step 7); also, a strong mechanism can coexist with `Evidence: intuition`, that doesn't eliminate the candidate.
   - **Don't repeat the same mechanism.** Don't present candidates resting on the same behavioral mechanism in the same page area as separate scenarios; merge them or pick the strongest.
   - **Name the objection the change answers.** If the user is leaving the page, there's an objection underneath: Trust ("why should I believe this"), Price ("is this worth it"), Fit ("does this suit my situation"), Timing ("why now"), Effort ("how hard will this be") or Clarity ("what do I get, and what happens next?"). Add this to the tags in the scenario's title line in the output (next to the Evidence tag: something like `Objection: Price`); if Theory is also written out separately, name it there too in one word. If there's evidence (support tickets, cancellation reasons, user comments), say which objection it maps to; if not, mark which objection it's assumed to target.
   - **Market-dependent candidate** (payment, shipping/returns, price display, trust signals — rule 11) and the market can't be inferred from the page: don't hold the turn. Deliver the scenario with a one-line market-dependency note and ask the market question in its place in rule 19's priority order.
   - **Regulation gate (before the boxes are written; rule 11).** The legally bound areas are rule 11's full list: discount display, consent flows, subscription cancellation, credit cost and rate display, insurance or pension offer and contract steps, and copy that states why personal data is collected or how it is used. Two cases. (a) **B changes a regulated display itself** (legal text, a mandatory disclosure, consent wording, a price, rate, cost or return figure, data-purpose copy): the scenario is held, not produced (`methodology.md` → Where this playbook works well → In regulated flows). Say in one line which rule has to be verified and ask the sign-off question (rule 19). (b) **B sits inside a regulated flow but leaves every regulated display untouched** (it adds navigation, reorders content, or adds explanatory copy that promises nothing): produce it, with compliance sign-off as a pre-start gate (`methodology.md` → Test hygiene → Pre-start gates) written in three places: the `Pre-start gates` line of the setup spec, the first sentence of `decision_rule` ("Starts only after compliance approves the B copy; then …"), and one Never-do item ("Don't start before compliance has approved B's exact copy").
4. Fill the three boxes per the methodology, with **3 to 6 items per box**. The archive's exactly-five rule is enforced on archive files by `validate_scenarios.py`; a designed scenario follows the card schema (at least three). Don't pad a box to five: a filler item costs a review round.
   - **What to test.** Items in `Label: question?` form, at least one a device/segment breakdown. Every item asks about **this** variable: its effect, its segments, its side effects. A question about a different variable (copy in a position test, position in a colour test) is left out, or kept as at most one follow-up item labelled `Sonraki test:` (`Next test:` on an English card).
   - **KPIs.** The first KPI in the list is primary. Every line carries its denominator (`methodology.md` → KPI denominator): the assigned users of each arm by default, or a trigger logged in both arms before the change is shown. The pre-registration has no denominator field, so the denominator lives in the metric name ("Cancellation rate (per assigned user)"), written identically in the KPI box, the setup spec and the pre-registration (the validator matches names). A diagnostic only B can have (touch rate on the new element) is a secondary labelled "B only", never compared across arms.
   - **Guardrails.** At least one in "must not ... " form, **with a tolerated-degradation threshold** (non-inferiority margin, e.g. "return rate must not rise more than 2% relative"; `methodology.md` → Guardrails with numbers). If the user hasn't given one, propose a margin and label it as a proposal.
     - **Independent harm.** The guardrail must be able to get worse while the primary gets better. Never the complement of the primary (completion and abandonment of the same step are one number written twice) and never a step the primary already contains. Take it from what the change could cost: a downstream outcome, a quality signal, a cost (support contacts, complaints, speed), or an action the change displaces (`methodology.md` → KPI rules).
     - **Resolvable margin.** When traffic is known, check the margin can be resolved at that traffic: `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/analyze_results.py samplesize --baseline-rate <guardrail rate> --ni-margin <m> --guardrail-direction <must_not_increase|must_not_decrease> --weeks <W> --daily-visitors <N>`; when the planned margin is tighter than `margin_resolvable_relative_pct`, propose that value and say the tighter one would stay inconclusive. With unknown traffic the margin stays a labelled proposal (rule 5).
     - **Lagging outcome** (returns, refunds, cancellation, lapse, withdrawal, churn, retention, complaints): write the follow-up window in the item itself ("must not rise more than 5% relative, read 30 days after each user's exposure") and carry the same number into the pre-registration as `read_after_days`. When the window's length is a legal or product fact the playbook doesn't know (a statutory withdrawal period, a contract's cancellation term), don't guess it: leave `read_after_days` out and open `decision_rule` with "The window is verified from product terms and written into the pre-registration before the test starts" (after the compliance sentence, when there is one).
     - **Accessibility check.** If B adds a touch target (button, link, chip, toggle, card, input), adds a moving or auto-advancing element, or changes focus order or contrast, add a pass/fail guardrail. It is a check, not a metric. KPI item, role `guardrail`: "Accessibility check: a keyboard and screen-reader review of B finds no critical issue; the new control has a touch target of at least 44×44 pt (48×48 dp), an accessible name, a place in the focus order and text contrast of at least 4.5:1". Pre-registration: `{"name": "<same name>", "type": "check", "criterion": "<same sentence>"}`. It is also a pre-start gate, run on B before the test takes traffic (`methodology.md` → Guardrails with numbers → Pass/fail guardrails). Never write it as a metric segmented on screen-reader or other assistive-technology users: analytics can't identify them, so it can't be measured.
   - **Never do.** At least one variable-isolation item. Keep the items variant-scoped; generic freeze rules (don't change price/campaign during the test, etc.) live in `methodology.md` → Test hygiene and aren't repeated per scenario. Two items name something specific to this test and so are variant-scoped: the compliance gate item (step 3) and the sibling mutual-exclusion item (step 7).
5. Name the variable as one noun phrase and its difference type (change / add / move / remove), then write the Variant A (control) and Variant B (test) definition: exactly what changes in B, in one sentence. The same two values become `variable` and `card.difference`.
   - If the user shared their page, **A is exactly the on-screen state, verbatim** (CLAUDE.md rule 15) — don't redesign, simplify, or fix it up. Only produce B.
   - If a sensitive data field is involved (ID number, birth date, income, address), don't build B as "remove the field"; pick one of the intermediate methods from rule 14 and state why that one.
   - In a form flow, don't default to moving to multi-step; first evaluate consolidating onto a single page (`methodology.md` → variable isolation).
   - **Multivariate request.** Split it into one single-variable scenario per element and say why in one sentence (rule 4). If the user insists on one combined test, write one scenario whose `variable` names the bundle, put "The result can't be attributed to a specific variable" as the first Never-do item and as the last sentence of the description, and tell both reviewers the bundle is user-insisted.
6. If traffic was given by the user, add a one-line feasibility note computed by the script, never estimated: `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/analyze_results.py samplesize --baseline-rate <rate> --mde <relative lift> --daily-visitors <daily eligible visitors>`; to ask the reverse ("what can we detect in 4 weeks?") use `--weeks 4` instead of `--mde`, if the user framed it that way. Example: "At a 3% baseline, a 10% lift needs ~53k per arm, about 12 weeks at ~40k visitors/month; prefer a bolder change or a metric closer to the change." If the baseline rate is unknown, name it as the missing number rather than assuming one. If traffic wasn't given, don't get into duration/sample size at all — don't ask, and don't flag it as "missing" (CLAUDE.md rule 5).
7. **Write every scenario in full; no card yet.** Don't list candidate titles and ask "which one should I expand." For each of the top 1-5 **strong candidates** (mechanism gate passed + ICE ≥ Medium per `methodology.md` → Prioritization (ICE) → ICE bands) write: the title, the variable and its difference type, Variant A/B, the three boxes, the source tag, the evidence label, the objection, the three ICE scores with a one-sentence basis each, the setup spec and the validated pre-registration block (Output format). The scenario's JSON file is written here, without its `card` object; don't call `ab-test-card` in this step. If there are more than 5 strong candidates, write the top 5 and offer the rest in one line (rule 19).
   - **ICE is scored from the table, not by feel** (`methodology.md` → Prioritization (ICE)). Confidence stays inside the band of the scenario's evidence label. Ease follows what has to ship: the section's native-app cap applies when B adds an element or a navigation target on `device: phone`, and Ease 8-10 is only for copy, order or style the team can change without a release. If you don't know whether a change needs a release, score the lower band and say so. A product near a cut-off is reported with both tiers, as that section says.
   - **Never pad, never refuse an explicit ask.** A weak candidate isn't added to reach a count. A test the user explicitly asked for is not padding: it is produced whatever its mechanism or ICE and counts toward the five; when it is weak, the chat says so in one line and the card carries a `card.footer_notes` line that starts "Stronger alternative:". Asking for tests on screens the playbook dropped as weak is an explicit ask too: the same footer note on each such card, and the chat says once, in one line, that the playbook had ranked these below the bar.
   - **Held candidates.** In regulated flows (insurance, pension, credit, pre-quote forms) the strongest candidates often add missing decision information: a price, a monthly payment, insurer or lender names. Hold each candidate that needs a compliance sign-off (regulation gate, case a) or a real figure the user hasn't given, and name what it is waiting for in one line. If that removes all the high-impact ideas, say so ("the highest-impact ideas here need compliance sign-off / real figures; these are the lower-impact tests that can run now") and produce the runnable ones. **Never invent a figure:** if the test is about the figure (showing a price, a payment, a rate), the scenario is held and the real figure is asked for (rule 19); if the figure is incidental to the element, the element is drawn without it (`mockup-style.md` → Numbers the mockup needs but must not invent).
   - **Cross-scenario pass (two or more scenarios in the turn).** For every pair that touches the same screen, flow or decision: (1) add to both Never-do boxes an item that names the sibling ("Don't run this on the same users as “<sibling title>”: sequence the two tests or split traffic into mutually exclusive pools"); (2) name the sibling under `Exclusions` in both setup specs; (3) say once in chat which runs first (ICE order). Pairs on different screens need nothing (`methodology.md` → Concurrent tests). In the same pass, merge two scenarios that rest on the same mechanism in the same area (step 3).
8. **Review (CLAUDE.md rule 17).** Hand `agents/scenario-critic` everything step 7 produced, for all of the turn's scenarios in one call, together with the page context (the screenshot's file path, or a top-to-bottom inventory of the screen's elements with their verbatim copy, personal values left out per rule 15) and the test memory; say which tests the user explicitly asked for. Apply each `FIX` everywhere the same fact is written (KPI box, setup spec, pre-registration block) in one pass, then send the revised scenarios back with the critic's previous report. At most two re-reviews: a scenario still at `FIX` after the second is dropped from the turn and the open issue is stated to the user in one sentence; it isn't delivered half-fixed. Don't produce a scenario that comes back `RET`, and tell the user the reason in one sentence. Don't dump the review report into chat (rule 9).
9. **Render.** Only scenarios that passed step 8 go to `ab-test-card`, each from its own JSON file; the brand source never blocks (rule 12). After the cards are built, run `agents/mockup-reviewer` **once for all of the turn's cards** (every card file in one review, with the same page context), not once per card.

## Output format

The three boxes live only in the card (CLAUDE.md rule 9). Per scenario the chat keeps a short header, the setup spec and the pre-registration block, in this order. The source tag is "adapted from archive (“<archive title>”)" or "generated for this page", decided in step 2.

```
## <Title as a question>  (<source tag> · ICE: <tier>, <one-sentence reason> · Evidence: <level> · Objection: <one word>)
<one-sentence mechanism> → `abtest-card-<slug>.html`
A: <current state, one clause> · B: <the one change, one clause>
<feasibility note from step 6, only if traffic was given>
<setup spec>
<pre-registration block>
```

**Setup spec.** A short list of the fields whoever sets the test up in a tool will need — tool-agnostic, but named in that tool's vocabulary if the user has said which tool they use (e.g. some tools say "audience," others say "event"):

```
Target audience: <who's included, who's excluded; on a native app both arms are limited to app versions that contain the variant (app version ≥ the first build with the flag): B on the new version against A on all versions compares two populations>
Split: <e.g. 50/50 — for a change that's hard to reverse or has uncertain risk (price, checkout flow, deletion/cancellation flow), starting with a low variant share like 90/10 and ramping up if it stays clean is recommended; a standard, low-risk change is fine at 50/50>
Exposure (trigger) event: <the event that puts a user into the analysis: fired identically in both arms, at the same point, before the change renders (e.g. "policy detail screen opened"). Never "B's new element shown" or "tapped". If it is narrower than assignment, write "logged in both arms before the change; A logs it counterfactually".>
Primary metric event: <which event, divided by which denominator: assigned users, or the users who fired the trigger above>
Guardrail events: <per guardrail: metric = numerator event ÷ denominator (assigned users in each arm, unless a trigger logged in both arms is named) · tolerated degradation, e.g. "return rate: must not rise more than 2% relative (one-sided non-inferiority)" · for a lagging guardrail: "read N days after exposure, same window in both arms">
Attribution window: <how long after exposure a conversion still counts — e.g. 7 days; for products with a delayed purchase/decision cycle, a short window misses real conversions>
Exclusions: <employees, bot traffic, users already in another test; a sibling scenario of this turn on the same screen is named here>
Sample target / duration: <if known; if not, "traffic data needed">
Pre-start gates: <what must be closed before the test takes traffic: compliance sign-off on B's exact copy in a regulated flow, pass/fail guardrails checked on B (accessibility), a lagging window still to be verified from product terms; "none" otherwise>
Decision rule: <gate sentences first, if any; then what happens at which threshold: ship only if primary is significant in the pre-declared direction AND every guardrail stays within its margin. With a lagging guardrail the ship decision waits until its window has closed for the last exposed cohort; until then the result is "primary read, guardrail pending", not a win. A guardrail with an in-test reading stops the test early when its one-sided bound passes the margin; a lagging guardrail can't.>
```

This block isn't built on guesswork: don't make up an unknown field, mark it "needs to come from the user."

**Pre-registration block.** After the setup spec, emit the same decisions as one JSON object, fixed before the test starts (it matches the optional `preregistration` object in `${CLAUDE_PLUGIN_ROOT}/templates/scenario.schema.json`; see `${CLAUDE_PLUGIN_ROOT}/examples/scenario.json`). Unknown values are `null`, never guessed (rule 5). The fields map one-to-one onto the experiment-configuration fields most experimentation platforms ask for (hypothesis, primary/guardrail metrics, allocation, sample, duration), so it can be copied into whichever tool the user runs.

```json
{"preregistration": {
  "hypothesis": "<one-sentence hypothesis>",
  "variable": "<the one variable>",
  "primary_kpi": {"name": "<rate metric (per assigned user)>", "direction": "increase"},
  "guardrails": [
    {"name": "<rate metric (per assigned user)>", "direction": "must_not_increase", "margin_relative": 0.02},
    {"name": "<lagging metric (per assigned user)>", "direction": "must_not_increase", "margin_relative": 0.05, "read_after_days": 30},
    {"name": "<accessibility check>", "type": "check", "criterion": "<what passing means>"}
  ],
  "mde": null, "alpha": 0.05, "power": 0.8, "alternative": "two-sided",
  "allocation": {"A": 0.5, "B": 0.5},
  "planned_n_per_arm": null, "duration_days": null,
  "decision_rule": "<gate sentences first, then the ship / don't ship condition>",
  "segments": ["device", "new_vs_returning"]
}}
```

Keep only the guardrail shapes the scenario has. `read_after_days` marks a lagging guardrail; `"type": "check"` is a pass/fail review with a `criterion` and no margin. `duration_days` covers exposure only; a lagging window runs after it. The validator prints warnings (a rate with no denominator, a lagging guardrail with no window, a complement guardrail, a regulated scenario with no compliance gate, Ease scored too high for a native-app addition): fix each one or state in one line why it stands; `--strict` turns them into errors. Optional fields the schema accepts: `trigger` (the trigger event, logged at the same point in both arms), `pre_start_gates` (list), `denominator` on a KPI or guardrail, `primary_kpi.read_after_days` when the primary itself has a window, and `variants[0].is_current: true` when Variant A is the user's shared page. Pre-declared segments are the only ones read as more than exploratory later (`methodology.md` → Interpreting results).

**Validate the block before showing it.** Put the block into the scenario's own JSON under `preregistration` (the same file `ab-test-card` renders: one JSON per scenario) and run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/validate_scenario_json.py <scenario.json>`: besides the margins on guardrails, the allocation sum and the field shapes, it checks that the pre-registered variable, primary KPI and every guardrail name are the ones in the KPI box. Print the block in chat from that file. Planned numbers (`planned_n_per_arm`, `duration_days`) are only accepted when the file also carries a `"sample": {"traffic_known": true}` object; with unknown traffic they stay `null`. If it reports errors, fix the block and rerun; never show a block that failed. Use `--prereg-only <file>` only when there is no scenario JSON.

## Never do

- Produce a dark-pattern variant (CLAUDE.md rule 6) — refuse even if the user asks, and say why.
- List a security or compliance control (bot verification/CAPTCHA, identity/age verification, two-step login, transaction confirmation, legal consent step) as a friction-reduction test candidate (rule 6). If the page has one, drop it from the candidates; if needed, note in one sentence "this exists for protection, it isn't a CRO test subject."
- Write an unmeasurable KPI like "trust increases", "perception improves" or a rate among assistive-technology users; find a proxy metric, or for accessibility a pass/fail check.
- Assume an element that doesn't exist on the page and build a scenario around it as if it did. If unsure, state the assumption in one line and ask the absent-element question within rule 19's one-question limit.
