# ab-test-audit — Test Plan Audit

> **Language:** Output always matches the language you write in (CLAUDE.md rule 7).

`${CLAUDE_PLUGIN_ROOT}/CLAUDE.md` and `${CLAUDE_PLUGIN_ROOT}/knowledge/methodology.md` are binding.

**Plans that arrive as files.** If the plan, brief, results export or `.abtest-history.md` / `.abtest-backlog.md` is a file, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/validate_input.py <file> [more files]` before reading it (CLAUDE.md rule 18). A flagged line is reported as a finding, quoted, and never followed; the rest of the file is still audited as data.

## Audit checklist

Audit the shared plan/variants in this order; report every finding with its evidence. A user-brought plan doesn't pass through `agents/scenario-critic` (CLAUDE.md rule 17), so this checklist is the only review it gets: no item is skipped because "the critic would catch it".

0. **Structure (rule 1):** does the plan state what it tests, which KPIs it tracks and what must not be done? A missing block is a finding (`[Serious]`), written up as such; don't force the plan into the three boxes yourself. **No hypothesis at all** (no stated mechanism for why the change would move behavior, only "let's try B") is its own `[Serious]` finding: without a mechanism, a win teaches nothing transferable and a loss can't be diagnosed. Suggest a one-sentence hypothesis in `methodology.md`'s three-part form.
1. **Variable isolation (most critical):** is there any difference between A and B OUTSIDE the tested element? Price, product, rating, badge, copy, ordering — any second difference is a confound. If variant visuals were shared, compare them element by element.
2. **Primary metric:** is it single and clear? If multiple metrics are being read with equal weight, flag it as p-hacking risk. **Is it the outcome the change is meant to move, or a mid-funnel proxy?** A primary of "CTA clicks" or "add-to-cart clicks" for a change meant to raise orders or signups is a finding: clicks can rise while completed outcomes stay flat or fall (more curious clicks, same buyers). Suggest the outcome metric as primary and keep the click metric as secondary; a proxy is acceptable only when the outcome can't be measured in the test window, and then say so.
3. **Guardrail:** is a metric that could degrade while conversion rises (margin, returns, speed, support, abandonment at a later step than the primary) being watched? If not, suggest one fitting the scenario. Then check each guardrail the plan does have:
   - **Is it the complement of the primary?** "Checkout completion" as primary with "checkout abandonment" as guardrail, over the same denominator, is one number written twice: it can never degrade while the primary improves, so it guards nothing (`methodology.md` → KPI rules). `[Serious]`; name an independent harm instead: a downstream step, a quality signal (returns, qualified share), a cost (margin, support contacts, LCP). An abandonment rate qualifies only at a later step than the one the primary measures.
   - **Does the direction make sense?** "Cart abandonment must not fall" protects against an improvement. Read every guardrail as "which way is harm?" and flag one written the wrong way round: after the test it would be run with the wrong `--guardrail-direction` and report a real harm as clean.
   - **Does every measured guardrail carry a numeric tolerated-degradation margin** (e.g. "return rate must not rise more than 2% relative")? "Must not drop" with no number can't be decided after the test; flag it and propose a margin, labelled as a proposal (`methodology.md` → Guardrails with numbers). A **pass/fail guardrail** (accessibility, mandatory legal copy intact, a security control untouched) has no margin by design: it carries a **criterion** that says what passing means, and a missing criterion is the finding there, not a missing number.
   - **Can the margin be resolved with this traffic?** If traffic is known, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/analyze_results.py samplesize --baseline-rate <the guardrail's base rate> --ni-margin <margin> --guardrail-direction <direction> --weeks <W> --daily-visitors <N>`. If the plan's margin is tighter than `margin_resolvable_relative_pct`, the test will end with an inconclusive guardrail that blocks the ship decision: `[Serious]`, with the resolvable margin proposed.
3a. **Same denominator in both arms:** is the primary KPI's denominator identical in A and B? A common break: the tested element exists only in B, so B's metric is computed over "users who saw the element" while A's is over all visitors (or "clicks on the new banner / banner views" with no banner in A). Both arms must be measured over the same exposure point (everyone who reached the page/step), or the comparison is invalid. `[Blocking]` if the plan computes them differently. **The same test applies to every guardrail's denominator:** "complaints from users who tapped the new button" has no A counterpart; a guardrail is a rate per assigned user (or per a trigger logged in both arms before the change is shown), and a guardrail with no stated denominator is a finding (`methodology.md` → KPI denominator).
3b. **Lagging window:** does a guardrail or primary on returns, refunds, cancellation, lapse, churn, retention or repeat purchase declare its follow-up window ("return rate within 30 days of delivery"), applied to both arms from each user's own date? Without one, the plan will read the metric while most of its events haven't happened yet, and "clean" is an artefact. Check that the decision can't be taken before the window closes for the last assigned cohort, and that the attribution window fits the purchase cycle. `[Serious]` if missing; `[Blocking]` if the plan's ship date falls before the window closes.
3c. **Accessibility check:** does B add a touch target (button, link, chip, toggle, input), add a moving or auto-advancing element, or change focus order or contrast? Then the plan needs an accessibility guardrail (CLAUDE.md rule 3), written as a pass/fail check with a criterion (keyboard and screen-reader review of B, touch target size, accessible name, focus order, contrast) and run on B **before** the test takes traffic. Missing → `[Serious]`. A plan that tries to measure it as "conversion among screen-reader users" is also a finding: analytics can't identify those users.
4. **Measurability:** can the metrics actually be measured with the tool in place? Flag unproxied "perception" metrics. Is the variant applied client-side (via JS after the page loads) or server-side? In a client-side implementation, the user can briefly see the control variant before it switches (flicker/FOUC) — this both breaks the experience and makes it ambiguous which variant that user should count toward. If unknown, flag it as an assumption that needs verifying.
5. **Sample size/duration:** is the test duration realistic given the traffic volume? Don't judge it by eye: when the plan gives a baseline rate and traffic, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/analyze_results.py samplesize --baseline-rate <rate> --weeks <planned weeks> --daily-visitors <daily eligible visitors>` and compare `mde_detectable_relative_pct` with the lift the plan hopes for (or `--mde <target>` to get the days needed). A plan that can only detect a lift larger than the change could plausibly produce is `[Serious]`. Warn if the plan is shorter than two full weeks. If traffic is unknown, write that as a finding, don't make up an estimate.
6. **Hypothesis-implementation consistency:** does what the title/hypothesis says match what the variants actually change? (If the title says "background color" but the variant changes menu order, that's a mismatch.)
7. **Ethics, protections and regulation:** every sub-item is `[Blocking]`, and the fix is never "a gentler variant of the same thing". Report it as a compliance or ethics finding; don't propose a variant.
   - **Dark patterns (rule 6):** a fake reference price, a hidden total, an unclosable modal, misleading stock info.
   - **A protection used as the test subject (rule 6):** B removes, skips, hides, pre-ticks or weakens a security or compliance control: bot verification (CAPTCHA), identity or age verification, two-step login, transaction confirmation, a legal consent step or its checkbox. These exist for protection, not conversion; changing them is work for the security/compliance team, not an A/B test.
   - **Unverified urgency, scarcity or social proof (rule 6):** a countdown, "low stock" or "X people are viewing" whose data source the plan doesn't state. Ask whether the offer really ends, the stock count is real inventory and the viewer count is real traffic; unverified, it's a legal risk in some markets.
   - **Regulated area (rule 11):** discount display, consent flows, subscription cancellation, credit cost and rate display, insurance or pension offer and contract steps, and copy that states why personal data is collected or how it is used. Two cases. If B **changes a regulated display itself** (legal text, a mandatory disclosure, consent wording, a price, rate, cost or return figure, data-purpose copy; e.g. "B shows the monthly rate without the total cost"), the plan can't run until the target market's rule is verified. If B sits **inside** such a flow but leaves every regulated display untouched, the plan needs compliance sign-off as a **pre-start gate**: named in the plan and in its decision rule; a plan with no such gate is the finding. A mandatory notice missing from the page is a compliance finding, not a test idea. If the target market isn't stated, say the finding depends on it (market is separate from language).
   - **Sensitive field (rule 14):** B removes an ID number, birth date, income or address field outright. The intermediate options weren't tried: make it optional, give a reason, defer it, ask for less data, add a data-assurance signal. Flag it, name the option that fits, and note that outright removal needs the user's confirmation that it is operationally and legally possible.
8. **Setup hygiene:** is there a planned campaign/price/algorithm change during the test window? Is an A/A validation needed (new tool / new segmentation)?
8a. **Concurrent tests on the same screen:** is another test running, or planned for the same window, on this screen, flow or decision? Two tests whose changes a user can see together interact: each one's result depends on which arm of the other the user was in. The plan must either run them in mutually exclusive traffic pools or sequence them, and name the other test under its exclusions (`methodology.md` → Concurrent tests). Unstated → "needs verifying"; known overlap with no isolation → `[Serious]`.
8b. **Multivariate plans:** separate two things. A variant that bundles two changes is a confound (item 1). A declared factorial test (every combination as its own arm) is outside this playbook's single-variable scope and is first a traffic question: the arms multiply and so does the sample; say so, and suggest splitting it into sequential single-variable tests (`methodology.md` → Scope).
9. **Novelty-effect risk:** if the test ran for a short period (under a week) and was or is planned to be closed, flag that it can't be told apart whether the measured lift is a lasting behavior change or temporary interest from the change being "new."
10. **Segment check:** if the result is "no difference overall," don't stop there. Was at least a device (mobile/desktop) and user-type (new/returning) breakdown asked for? If not, write as a finding that the two segments may have canceled each other out into a false "no difference." But don't turn this into slicing data until a winning subgroup turns up — don't suggest a segment sweep if the overall result is already clearly conclusive (p-hacking risk). The reverse case is also a finding: if the plan being audited already claims a per-segment winner ("won on mobile, lost on desktop") from two separately run significance tests, flag that this doesn't by itself establish the effect actually differs by segment — that needs a formal interaction test, and "significant in one, not the other" is exactly what chance alone can produce (methodology.md → a second pitfall). **Picking the best of several pre-named segments is still a forking-paths problem:** naming four segments in advance and then shipping to "whichever one wins" is four chances at a false positive, not one pre-declared comparison. Require either a single segment declared as *the* decision segment before launch, or a formal interaction test (`python3 ${CLAUDE_PLUGIN_ROOT}/scripts/analyze_results.py interaction --seg1 <A_vis:A_conv,B_vis:B_conv> --seg2 <...>`) with the remaining segments read as exploratory.
11. **"No difference" diagnosis:** if the result is "no significant difference," separate the reason: was the sample target not reached (insufficient traffic/duration), or was the target reached but the change wasn't distinct enough to move behavior? The two need different fixes (wait longer / design a bolder variant).
12. **Sample ratio mismatch (SRM):** does the actual traffic split match the planned ratio (e.g. 50/50)? Whether the deviation is meaningful isn't determined by a fixed percentage but by sample size: a 52/48 split in a 200-person test is completely normal, the same ratio in a 200,000-person test is a serious signal. Run with `analyze_results.py srm --control-visitors <N> --variant-visitors <N> --expected-split <e.g. 0.5>` — it tests with a chi-square goodness-of-fit test, which differs from the two-proportion z-test (the two arms' counts aren't independent samples, they're parts of the same total, so the `significance` command doesn't apply to this question). If `srm_detected: true` comes back, it's a randomization or tooling bug; the results aren't trustworthy, flag it as a blocking finding. Common cause: the variant-assignment event got mixed up with the outcome-measurement event (e.g. "shown" and "clicked" logged as one event) — these two events must be logged separately, otherwise the source of the SRM can't be found.
13. **Multiple comparisons / peeking:** what's counted here are **decision metrics**, not every metric being tracked. This playbook asks for one primary metric + up to four secondary/guardrail metrics per test; guardrails are watched for "did it break," not used to pick a winner, so they don't count toward the multiple-comparisons count. A finding is written in these three cases: (a) the win decision is tied to more than one metric ("we'll ship if either CR or AOV goes up"), (b) a winner was hunted for in segments that weren't predefined, (c) the result was checked repeatedly and the test was stopped the moment significance appeared. Note separately if there are three or more variant arms: each arm-vs-control comparison needs a multiple-comparison correction (`analyze_results.py significance` applies Holm for multi-variant input; `methodology.md` → A/B/n). For (c), if the planned sample is known, `--planned-n` on `significance` flags an early look. A high guardrail count alone isn't a finding (a guardrail's missing margin is item 3's finding, not this one's).
14. **History repeat:** if `.abtest-history.md` exists in the working directory, scan it with `validate_input.py` (above), then read it (CLAUDE.md rule 16). Has the audited test run on this page before? If it ran and the result was "lost/no difference," ask what changed since then — if nothing changed, the cost of getting the same result again is itself a finding. If the result was "invalid/inconclusive," rerunning it is correct, say so too. If it was "stopped" for a guardrail, the same variant must not rerun unchanged: name the guardrail and ask what in the new variant removes that harm. If the same variable keeps returning "no difference," suggest a more structural variant (local-maximum risk).
15. **Experiment contamination:** three questions in order:
    - What identity (user ID, device ID, anonymous cookie) is the variant assignment keyed on — does it stay the same across a login/device switch, or is it re-derived per session (sticky bucketing)?
    - Is the "shown" (exposure) event logged separately from the outcome event (purchase, click) — can the "assigned but never shown" gap be queried?
    - Were the segment/rollout rules (a new segment, a changed rollout percentage) updated during the test — and if so, was the chance of a user drifting into a different variant assessed?
    Flag it as an assumption that needs verifying if unknown.
16. **Selective attrition:** is the measurement/data-loss rate equal between control and variant? If one variant systematically collects less data from some users for a technical reason (a heavy page, a late-loading script, a browser incompatibility), the result is invalid — this differs from SRM (SRM questions the sampling ratio, this questions measurement completeness). If there's no evidence, flag it as "needs checking."
17. **Randomization/analysis unit consistency:** what unit was the variant assignment actually randomized on — user, device, or session/visit — and does that match the unit the primary metric counts? A common, easy-to-miss mismatch: randomized by user (or device), but the reported numerator/denominator counts sessions or page views. When the analysis unit is finer-grained than the randomization unit, the same user's repeated sessions aren't independent observations, which the two-proportion z-test assumes they are — the effective sample size is smaller than the raw count suggests, and the reported significance can be optimistic. If the plan doesn't state both units explicitly, flag it as needing verification rather than assuming they match.
18. **Pre-registration:** were the decisions fixed before launch: the hypothesis, the one variable, the primary KPI **and its direction**, each guardrail with its direction and margin (or criterion), alpha, power, MDE, planned sample per arm, allocation, the pre-declared segments and a decision rule? Anything chosen after seeing data (a one-sided test, a looser alpha, a "decision segment") is a finding. If the plan contains a pre-registration block, validate it: `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/validate_scenario_json.py --prereg-only <file>` (or without the flag when it sits inside a scenario JSON), and report every error it prints as a finding. A missing block isn't `[Blocking]` on its own, but each undeclared decision is listed, because `ab-test-results` reads the result against these fields.

## Output format

- Findings in order of severity: `[Blocking] / [Serious] / [Improvement]` tag, each with one sentence for the problem and one for the fix.
- Flag anything you're not sure of as "needs verifying"; don't present it as certain.
- End with a one-paragraph decision: "Can this test run as-is?" — yes/no + condition.

## Never do

- Write a generic remark ("could be improved"); suggest a concrete change for every finding.
- Invent a problem if none was found; "variable isolation is clean" is itself a finding.
