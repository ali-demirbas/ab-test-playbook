# ab-test-card: Scenario Card Rendering

> **Language:** Output always matches the language you write in (CLAUDE.md rule 7).

`${CLAUDE_PLUGIN_ROOT}/CLAUDE.md` is binding. This skill holds what `ab-test-suggest` and `ab-test-design` share: drawing a record's card and the Delivery pipeline. It runs for every scenario they produce (rule 9) and when the user says "make a card".

## Reading

Once per session, nothing more at the start of a turn: this file, `${CLAUDE_PLUGIN_ROOT}/templates/record-checklist.md` (writing or changing a record: the skeleton and the first-validation list) and `${CLAUDE_PLUGIN_ROOT}/knowledge/mockup-style.md` (the card's core). Never the schema or the worked example: the skeleton replaces both, and a refusal names its fix; the card template only for raw markup. A file in `${CLAUDE_PLUGIN_ROOT}/knowledge/mockup-style/` only by the trigger table at the top of the core (a fold, pinned bar, stages or modal; raw markup; fast mode; the UNVERIFIED preview; a render_check finding).

## The card object

`card.screen` + `card.change` (+ `card.soft`) are the default way to draw (`mockup-style.md` → Screen spec): the builder compiles both arms, so A and B cannot differ anywhere else, and records on one shared screen carry the same `screen` list. Raw `card.variant_a` / `card.variant_b` only for what the list can't express (`raw-markup.md`), never both forms. `card.url` is required for `web` and `phone-web`; `card.mockup_basis`, `card.brand` and `card.inherited_contrast` as the core says (Realism level, Ring and label). Rare, normally left out: `card.bottom_nav` / `card.bottom_nav_active` (`phone` only) and `card.mobile_toolbar` (`phone-web` only), as in Frames; `card.stage_captions` (`special-cases.md`); `card.theme` (`dark` for a dark deck); `card.note_pos` (`above`, `below`); `card.phone_scale`, `card.web_scale`, `card.device` (overrides); `card.difference`, else equal to the record's `difference` (`değiştir` / `ekle` / `taşı` / `kaldır` spell the same four), a mismatch refused.

## Delivery pipeline

Binding for every card (rules 4, 9, 10, 17); `ab-test-suggest` and `ab-test-design` point here. One reviewer call per stage covers all of the turn's records or cards. Every command below runs in the main session, never through a subagent (rule 17), copied as one line.

1. **Validate** every record of the turn in one call: `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/validate_scenario_json.py <a.json> <b.json> <c.json>` (messages in each record's language). An error stops: fix and rerun. A warning is fixed, or its reason goes to the critic. Then the chat lines, the same files in the turn's order: `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/validate_scenario_json.py --chat <a.json> <b.json> <c.json>` prints every line a record fixes (per scenario the title, the tag line with the score, `Neden:`, `Doğru olmalı:`, `Önce yokla:`; after the list `Koşullu`, `Başlamadan önce:` and the stakeholder brief for scenario 1). They go into the planned chat as printed, never composed; what it can't print (a `Neden:` for a mechanism over 140 characters) its stderr names, and you write that line.
2. **Scenario review, one round.** `agents/scenario-critic` gets every record file and what the producing skill lists. Per record it returns `PASS` with the stamp JSON `build_card.py --critic-stamp` printed, alone or with `[fixable]` lines, or `FIX` (at least one `[blocking]` line) or `RET`.
3. **Critic stamp and fixes.** Write the stamp exactly as returned, `"review": {"scenario_critic": {"verdict": "PASS", "fingerprint": "<hex>", "safeguards": {…}}}`; then apply every `[fixable]` line as written (only rule 17's small-fix fields, adding or rewording, never removing a warning, criterion, invariant or exposure, so the stamp stays valid) and every `chat:` line, and rerun step 1 (validation and `--chat`) on the changed records. No re-call. A `FIX` is reworked and goes back through steps 1 and 2 (Loops).
4. **Draft.** With `card` in the record (added now if it wasn't written with it): `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/build_card.py --draft --template ${CLAUDE_PLUGIN_ROOT}/templates/scenario-card.html --scenario <record.json> --out abtest-card-<slug>.draft.html`. It refuses without a matching critic stamp, compiles `card.screen` + `card.change` into the two arms when the record uses them, runs the card checks, writes the draft and its manifest (`<out>.manifest.json`) and prints their paths with the `--stamp` command the reviewer runs on PASS. The draft carries no fingerprint. A record with a critical assumption builds a koşullu kart (conditional card), never a final one: ribbon "KOŞULLU · doğrulama gerekli" / "CONDITIONAL · needs verification", summary "conditional card (not implementation-ready)". Then `node ${CLAUDE_PLUGIN_ROOT}/scripts/render_check.mjs --strict --shot --half <draft.html>` measures it (Node.js 18 or newer with Playwright and Chromium, installed once outside any project: `npm i --prefix ~/.abtest-visual playwright && npx --prefix ~/.abtest-visual playwright install chromium`; render_check finds it there on its own) and saves the full- and half-size PNGs. Exit 0 `VERIFIED` → review; 1 `VISUAL_CHECK_FAILED` → fix every error, rebuild, rerun; 2 usage error → fix the command; 3 `VISUAL_CHECK_UNAVAILABLE` → nothing was measured: the reviewer's verdict is `UNVERIFIED`, never PASS, so no card becomes final (step 8). Look at the PNG yourself.
5. **Mockup review.** `agents/mockup-reviewer` gets every draft with its manifest, its record, the render_check output and PNG (or a line that it couldn't run) and, for a shared page, the screenshot path or an element inventory (personal values left out). It judges what the drawing means (variable shown, labels true, ring tight, neutral A/B, nothing unverified as fact), not only what render_check measures. On PASS the reviewer runs `build_card.py --template … --scenario <record> --stamp <draft.html>` (it writes nothing and refuses a draft or manifest the record no longer builds) and returns the JSON line it prints.
6. **Mockup stamp.** The JSON line the reviewer returned, `{"verdict": "PASS", "fingerprint": "<hex>"}`, into `review.mockup_reviewer`, exactly as printed.
7. **Final or conditional build** in the user's working directory: `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/build_card.py --template ${CLAUDE_PLUGIN_ROOT}/templates/scenario-card.html --scenario <record.json> --out abtest-card-<slug>.html`. It writes only when both stamps match; on refusal nothing is written and an existing file stays. It also writes the card's image, `card-<name>.png`, next to the card and prints its path (`--no-png` skips it; without Node or Playwright it says so in one line and still succeeds). It prints the final card's fingerprint. A share image, an overview or a later `--check`, only when the user asks: `draft-and-final.md`.
8. **Deliver** only that card, a conditional one named "koşullu kart" in chat, never final. Drafts and manifests are working files, never delivered or linked, with two exceptions (rule 9): fast mode's quick drafts (below), and the UNVERIFIED preview when the visual check was unavailable (exit 3): the draft, labelled UNVERIFIED and never called final, with the one calm chat line `draft-and-final.md` gives. Once the check is installed the same draft is checked and finished from step 4. The final build still refuses without a mockup PASS stamp (code); that no PASS is given without a render is a review rule (process).

**Loops.** Critic `FIX` → rework its `[blocking]` lines (a fix needing a fact the user didn't give becomes a critical assumption), back to step 1 and a re-call with the previous report. Mockup FIX `route: render` → fix only the mockup, `card.*` or the title's wording (a small-fix field: the critic stamp stays), rebuild the draft, resend; `route: scenario-critic` → back to step 1. At most two re-calls per reviewer; `RET`, or still FIX → not delivered, one sentence to the user. **Confirmed assumption:** remove it from `assumptions` (a covered change: the critic stamp no longer matches), back to step 1; the new final card carries no ribbon.

**Never** write a stamp without a PASS or with a fingerprint not printed by the scripts, run `--critic-stamp` or `--stamp` yourself, edit a draft into a final, or work around a refusal: it names the failed gate or field; fix the input.

## Fast mode

Rule 17's exception, only when the user asks for it (`ab-test` → routing table): the same records and chat, the validator only, one quick draft per record (`build_card.py --quick`, ribbon "Hızlı taslak · incelenmedi" / "Quick draft · not reviewed"), never called final; "tamamla" / "finish" runs both reviews. The steps and the chat line: `${CLAUDE_PLUGIN_ROOT}/knowledge/mockup-style/fast-mode.md`, read then.

## Never do

- Put any record text but the title on the card (no description, boxes, tags, notes, footer), or render a card for a record the validator refuses (rule 9).
- Render a dark-pattern scenario, even on "make the card" (rule 6).
- Escape text fields by hand (`&lt;` shows up as `&amp;lt;`); raw markup's own escaping and allowlist are in `raw-markup.md` (rule 18). A build warning (`build_card: warning: …`) is read, not ignored.
- Put a second difference in the mockups, draw a tab bar on a page that isn't a native app screen, or copy personal data from a screenshot (rules 4, 15).
- Color elements with inline `style` instead of `card.brand`, add an external font or CDN link, pull a logo from a URL, or ask about or note the brand (rule 12).
- Render in a language other than the user's (rule 7); a Turkish card sets `lang: "tr"` and uses curly quotes.
