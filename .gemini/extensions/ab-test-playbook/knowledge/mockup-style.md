# Visual Language — Scenario Card and Mockup Rules

`ab-test-card` and `templates/scenario-card.html` follow this spec. Source: the archive's visual deck (an internal design reference kept outside the repo — no visual files are added to the repo).

## Neutral palette and brand

Without a brand guide (rule 12b), the card is produced with these colors: the three boxes' identity colors are teal `#08616b`, amber `#6b3804`, navy `#17086b` (header strips); the primary CTA inside the mockup is the template's default orange (`#ff6a00`); the changed-element ring is red (`#e62d37`). This palette is deliberately brand-neutral.

The mockup's brand color is a CSS variable, not a hard-coded value: `--brand` (fills `.r-cta`, `.r-header.filled`, the active tab, checked boxes, the progress bar), `--on-brand` (text on that fill) and `--brand-name` (an empty `.r-logo` prints it). The card JSON sets them once with `card.brand: {"primary": "#c9392b", "on_primary": "#fff", "name": "Brand"}`; no inline `style="background:…"` overrides on individual buttons. Only plain color syntax is accepted (hex, `rgb()`, `hsl()`, a color name). The three boxes and the ring never take the brand color.

## Card layout

- A horizontal card, two regions: **the mockup pair on the left**, **the text column on the right**, and a muted **footer** across the bottom.
- The mockup pair: `Variant A` (control) on the left, `Variant B` (test) on the right. Both carry a green pill label above them (`Variant A` / `Variant B`, in every language).
- The right column: a question-form title at the top (bold, ~2 lines), a 2-3 sentence description below it, the three boxes below that.
- **Web cards** (`device: web`) give the mockups the extra width and keep the text column at a fixed 580px with slightly tighter type, so two desktop frames fit side by side and the card stays close to landscape (1600 wide, about 900-1000 tall). Phone cards keep the 54/46 split.
- **Footer**: (1) a tags line: source ("from archive", "adapted from archive (“archive scenario title”)" or "generated for this page", rule 8), evidence level (rule 10), the objection the change answers, the ICE tier with its scores; (2) the brand note (rule 12); (3) the mockup disclaimer when the mockup isn't a redraw of a shared page ("representative example" or "rebuilt from your description"); (4) any extra one-line note (`card.footer_notes`, e.g. "the address bar URL wasn't visible; it's representative"). All of it is escaped text, generated by `build_card.py` from the scenario JSON; none of it is written inside a mockup.

## The three boxes' style

Each box: a colored gradient header strip + a white body card.

| Box | Header strip | Header text color |
|---|---|---|
| Test edilmesi gerekenler ("What to test") | Cyan/turquoise gradient | Dark teal `#08616b` |
| Takip edilecek ana KPI'lar ("Primary KPIs to track") | Yellow/amber gradient | Dark brown `#6b3804` |
| Yapılmaması gerekenler ("Never do") | Purple/lilac gradient | Dark navy `#17086b` |

- Header: bold, ~20px equivalent. The header text follows the card's `lang` (Turkish or English).
- Body: a bulleted list, each item's `Label:` part **bold**, the rest normal; text color black at ~60% opacity. The builder adds the colon when a label lacks one.
- KPI items carry a **role pill** before the label: Birincil / Guardrail / İkincil (Primary / Guardrail / Secondary in English), from `kpis[].role`. The first KPI is the primary one (rule 2).
- Boxes carry a light shadow, rounded corners (radius ~17), a soft/dashed-edge feel.

## Realism level

The mockup is produced **fully realistic**: text, prices, labels, and layout are all real. Gray placeholder boxes stand in only for **a photo** (a product image, an avatar); never used in place of text. Filler phrases like "Heading," "Lorem ipsum," "Text field" aren't accepted.

**What "realistic" means: the user's own page, not a made-up one.** This distinction is the card's single most critical rule.

- **If the user shared a page (screenshot, URL, or flow):** the mockup is a redraw of that page. Product name, price, button copy, field labels, section order, menu items — whatever's on screen is what gets written. Variant A is exactly the on-screen state (CLAUDE.md rule 15): it isn't redesigned, simplified, made "better," or completed. Variant B differs from A in exactly one element. Building an e-commerce page from your own head and fitting the test onto it isn't realism, it's fabrication, and it's a rule-15 violation. (`card.mockup_basis: "shared_page"`, no disclaimer.)
- **If a detail can't be read from the screenshot** (cut-off text, a hidden section), don't make it up: either leave that part out of the mockup entirely, or ask the user. Filling the gap with plausible-looking content misrepresents the user's page.
- **If the page is only described in words** (no screenshot, no URL): the mockup is rebuilt from the description with realistic assumed copy that fits it. Where the market isn't known, the copy stays market-neutral (no invented brand, no local payment method or legal phrase the description didn't mention). The footer says so: "rebuilt from your description" (`card.mockup_basis: "described"`).
- **If there's no page in the picture at all** (a generic scenario from the archive, `ab-test-suggest` output): a representative example is built, and the footer says it's a representative example, not a real site's screen (`card.mockup_basis: "representative"`).

### Personal data is never copied

Values typed into fields in a screenshot (name, e-mail, phone number, ID or tax number, card number, address, licence plate) are **the user's input, not page state** (CLAUDE.md rule 15). They are never carried into the mockup, the scenario JSON or the chat. The field is drawn in its **empty default state**: its label, and its placeholder if one is visible (`<div class="r-label">E-posta</div><div class="r-field empty">E-posta adresiniz</div>` when that placeholder is really on the page; otherwise an empty field). A pre-selected default the page itself ships (a dropdown that loads with "30-65") is page state and is kept.

**Derived personal figures are personal data too** (`knowledge/methodology.md` → Variable isolation). Whatever the page computes from the user's own account is never copied from a screenshot: balances and accumulated amounts, allocation percentages, pie or ring chart slices, return rates, contribution amounts, contract or policy numbers, plan codes. The mockup keeps the structure and drops the values:

- Amounts are masked as "••• TL" (the page's own currency label), contract numbers and plan codes as "•••".
- A chart is drawn with neutral, equal slices and no percentages or legend values (a plain gray ring, or equal gray segments with inline styles); the real proportions are never reproduced, in size or in color.
- Masked areas are identical in A and B. `card.brand` takes the page's brand colors, never the colors a chart uses to encode the user's own allocation.
- If the test is about such a figure, hold the scenario and ask for a sample value the user is allowed to share (rule 19).

### Numbers the mockup needs but must not invent

Some scenarios need a figure on screen: a monthly payment, an interest rate, an insurance premium, a "from X" price, a credit cost. These are **regulated displays** in most markets (rule 11) and they are personal (they depend on the user's own inputs). A sample figure on a card reads as a real quote. So:

- If the test is **about the number** (showing a monthly payment preview, adding a "from" price): don't draw a made-up figure. Hold that scenario, say why in one line, and ask for a real figure the user's page shows today (this is the turn's one question if it's the highest-priority one, rule 19). A figure the user then supplies in chat for this purpose is page state: it is drawn as given, identically in both variants.
- If the test **isn't about the number** but the element happens to contain one: draw the element without the figure (the label, the layout, a "Teklifinizi görün" style line) rather than inventing a value.
- Plain shop prices visible on a shared screenshot are page state and are copied as they are; amounts are always identical between the two variants.

### Photo backgrounds

A hero with a photograph behind it is drawn as `.ph.hero`: a dark gradient block standing in for the photo, with white text on top (`.r-h`, `.r-sub`, `.r-name` turn white inside it). Never put dark text on a pale gray "photo" block, and never describe the photo in words inside the mockup.

There's a known cost to full realism, and whoever presents the card should know it: **a design that looks finished suppresses the viewer's structural objection.** People tend to comment at the color and wording level on a screen that looks complete, rather than saying "this flow is built wrong." This risk isn't addressed by simplifying the mockup, but by two things:

- The changed element is marked with a ring, and the ring's label states what changed; so attention goes to the tested variable, not a cosmetic detail.
- The card's text column (the three boxes) is always presented together with the mockup; what gets discussed is the questions there, not the mockup itself.

## Mockup rules

- **Only the tested element** differs between the two variants. Product name, price, rating, badge — all of it stays exactly the same.
- Inline colours inside a variant are page state, never decoration: a colour that exists only in B (a brand-coloured bullet, a tinted row) is a second variable unless the colour is the tested variable.
- **Linked differences are allowed and labelled, not a second variable.** When the tested variable directly causes another visible change (an "annual by default" toggle shows annual prices; a removed field makes the form one row shorter), that consequence is part of the one variable. It's drawn, and the ring's label or a shift note names it ("annual default, prices shown yearly"). A change that the variable doesn't force (also recoloring the button) is still a second variable.
- The tested difference is highlighted with a **red rounded ring** drawn as an outline (3px, offset 4px, a slight glow). An outline takes no space in the layout, so a ringed element sits exactly where its un-ringed twin sits in the other variant; a ring must never push content down. For the same reason the `.hl` wrapper carries no margin, padding, border or background of its own: if a ringed group needs breathing room, it comes from the children's existing spacing, never from the ring. `build_card.py` refuses an inline `margin` or `padding` on a `.hl`. The ring surrounds only the changed element, it doesn't cover the whole screen.
- **The ring carries a label.** A short label states what changed (`.hl[data-note]`, e.g. "coupon field collapsed," "delivery date added"). An unlabeled ring forces the reader to compare the two screens and find the difference themselves; the card's job is to state that difference. The label doesn't exceed two or three words. It sits just outside the ring's top-right corner; if it would cover a neighbouring element's text, put it below (`data-pos="below"` on that ring, or `card.note_pos: "below"` for the whole card). `scripts/render_check.mjs` reports labels that cover text.
- **On a stepper, ring the single changed step,** not the whole bar (unless the bar itself is the variable). The label goes below (`data-pos="below"`), under the step label, so it covers neither the digits nor the neighbouring steps. In a numbered-circle stepper the digit stays inside its circle and the step label sits under the circle, never beside it (the row has no width for it); circles, digits and labels are identical in A and B except for the tested step.
- **The difference type decides where rings go** (`card.difference`, the archive's "Fark:" line; `build_card.py` refuses a card that breaks this):
  - **change** (değiştir): ring the changed element in B; ringing its old state in A is optional.
  - **add** (ekle): the element exists only in B, so only B carries a ring; A carries none.
  - **move** (taşı): ring the element in both variants, at its old place in A and its new place in B, with the same label. The element itself (copy, size, style) is identical in both; only its position changes. If moving it also leaves a gap or shifts content, that consequence is a linked difference, noted under the mockup.
  - **remove** (kaldır): ring the element in A; B carries no ring (see below).
- **One change applied to N repeated elements gets one ring around the group,** not N rings (six product cards whose buttons all become filled: one `.hl` around the grid, labelled "buttons filled"). N rings read as N variables.
- **If an element is being removed (present in A, absent in B), the ring is drawn on the element in A, and that area is genuinely left empty in B.** A dashed placeholder saying "this element isn't shown" or "removed" isn't put there — a placeholder both reads like a permanent rule and misrepresents the variant: in the real B, that area doesn't exist, and the content below it shifts up naturally. This shift is preserved in the mockup, because it's often part of the test's benefit (the real content moves higher on the screen). To make the shift noticeable, a one-line note is dropped **below** the mockup with `card.shift_note_b` (required for a removal; e.g. "coupon field removed, the content below shifted up"); this note isn't written inside the screen itself.
- **Modal over a tab screen.** When B adds a modal (`difference: add`), A shows the full underlying screen (status bar, content, tab bar) and B shows that same screen under `.r-overlay`, the tab bar still drawn beneath the dimming. The ring goes around `.r-modal`, not the overlay; the dimming is a linked difference and isn't ringed. When the test is inside an existing modal, both variants draw the modal over the same screen and the ring marks the changed element within it. A card never pairs a modal screen with a different tab: that is two differences.
- **Device frames** (`device` / `card.device`):
  - `phone` = a **native app** screen: phone frame with a status bar (clock, signal, battery). A bottom tab bar is drawn **only if the real app has one**, with its own labels via `card.bottom_nav` (a list of labels). The tab the screen belongs to is marked with `card.bottom_nav_active`, given as that tab's label or its 0-based index, and drawn in `--brand`; a real app screen always has one active tab. The same tab is active in A and B: a different active tab is a second variable. Inventing a tab bar is the same realism error as inventing any other element.
  - `phone-web` = a page in a **mobile browser** (landing, form, checkout, most shared mobile screenshots): status bar plus a mobile address bar with a lock and the domain from `card.url`. Never a tab bar: a website has none.
  - `web` = a **desktop browser** frame: three dots and an address bar in the top bar, a white body. No status bar, no tab bar.
- Copy language and currency follow the user's page (rules 7 and 15): an English/USD page isn't translated into Turkish/TRY. With no shared page, the mockup copy is written **in the user's language**, and the currency is stated only when the market is known; otherwise prices are left out unless the test needs them. Amounts are always identical between the two variants. The card frame's language (`lang`) is the user's language too.

## Typography

- Primary font: Inter (headings Bold/Semi Bold, body Regular), with system fallbacks; the card loads no font file and opens offline.
- Full support for Turkish characters is required; character drops like "Baslık," "İndrim" aren't accepted.
- Quotes are curly ("…" and '), straight quotes aren't used.
